# LocalMind 0.5 架构修订

日期：2026-10-21。依据：0.4 的真实本地对照与故障复现。0.5 已实现共享模型投影、单次预算化 recall 和明确编号解引用，本轮 100 项开发回归通过。同一 11 个开发场景已重跑：MCP 11/11、编译上下文 10/11、完整有效历史 11/11；这属于已见开发集合改善，不能当作未见验收或长历史效果。交付状态以本轮验证报告、代码和能力报告为准。内部持久协议仍见 [PROTOCOL.md](PROTOCOL.md)，旧 [ARCHITECTURE.md](../ARCHITECTURE.md) 保留为 0.2 设计背景。

## 1. 本轮要改什么

目标仍是本地持有经历、当前任务和可追溯状态，让每轮推理少解释背景、及时采用纠正。MCP 只是其中一个读取入口。常驻观察、黑板调度、结果学习和云端执行器协作属于完整产品方向；当前 P0 尚未实现这些完整能力。

本轮优先修正“记忆存在，但模型读起来费力且更贵”的问题：将本地审计对象与模型输入分开，核心入口和 MCP 共用同一套证据投影与预算规则，明确序号指代的含义，再处理自然纠正和语义召回。暂不新增完整 Agent 框架、图数据库或微调。

## 3. 数据面与模型面分开

| 层 | 持有内容 | 外发原则 |
|---|---|---|
| 事件与当前状态 | 原话、身份、范围、事项修订、删除/暂停代次 | 继续由程序持有，不由模型输出重写权威 |
| 内部上下文与审计 | 完整来源 ID、snapshot、选取理由、依赖闭包、用量 | 留在本地，用于失效校验、故障定位与回放 |
| 模型可读投影 | 当前有效事项、必要原文、原始角色、精简引用、未知项 | 相同正文一次，完整条件不能因去重而丢失 |
| 接入层 | 自控消息、MCP recall、按需展开 | 复用投影；宿主能力与总窗口分别标明 |

模型投影不直接序列化整个 Store/state/packet。使用一次请求内的短来源标识映射到本地真实 Event；状态与决定引用同一来源表。原始用户输入在自控入口原样发送，在原生宿主已有输入时不重复注入。模型看到的来源仍带 user/assistant/tool 身份，历史文本不能提升为系统规则。

去重针对同一来源及其相同完整摘录，不把不同事件的相同文字当作同一经历。来源同时支撑多个事项时，列明当前仍有效的事项；其他历史值不能恢复为当前要求。投影前后都要能映射回原来源与有效版本。

## 4. 一个预算化 recall，而非客户端拼三份结果

已新增的 `localmind_recall` 使用启动时固定的 scope，接收 query 和补充预算；模型不能指定项目、数据库、角色或权威。默认补充预算 8192 字节，允许范围 1024–32768 字节，返回明确标记 `budget_scope=supplement_only`。执行次序为：读取当前版本 → 范围/有效性过滤 → 候选召回 → 依赖与指代解析 → 去重投影 → 预算选择 → 版本复查 → 返回。

state/search/expand 可保留给诊断和定点回查。正常补充优先调用 recall，避免每个宿主自行拼接一套行为不同的上下文。它只读、不采集查询、不创建用户要求，也不缓存跨请求正文。

实现中，`context.to_messages` 和 `MemoryReader.recall` 共用 `localmind/projection.py`。内部 packet 继续保留完整审计字段，模型视图只输出状态、单次来源表、已解析选择与未知项。

预算优先保留当前有效关键要求、必要证据和指代前件，其次保留相关历史。可选候选以完整条目为单位舍弃，不能裁去否定、数字或许可前提。必需内容装不下返回 BUDGET_INSUFFICIENT。去重、筛选之后再计量真实序列化字节数，记录省略原因和降级状态。

预算覆盖范围必须准确：自控入口可计算自身 system、历史、补充和当前输入的合计；MCP 服务只能保证其返回补充的大小。宿主需要另行预留已有历史、工具定义、当前输入和输出窗口。复用投影不等于取得宿主完整请求的控制权；不可观测项继续为 unknown。

## 5. 指代与纠正先解决含义

明确选择编号时，保存的用户字面值仍可为“第二个”。只在用户确认指向固定的原始助手提议、列表编号连续且唯一、选择没有否定或条件歧义时，投影额外提供 `resolved_choices.selected_option`、解析方法及用户确认/原提议两个来源。严格格式辅助函数位于 `localmind/choices.py`。这是有证据的解释，不改写历史原话，也不把助手建议独立升级为用户决定。

不明确的编号、多组列表、缺失选项、删除来源或“不要选第二个”等输入不能强行解析。优先保留未知项和必要前件，由当前用户输入消歧。不能通过绑定后来出现的另一份方案表来“修复”旧决定。

自然语言纠正分成三种结果：

| 定位结果 | 当前状态处理 | 模型输入 |
|---|---|---|
| 已唯一定位且新值可核验 | 受信程序提交事项新版本，失效旧依赖 | 当前原话、新状态及依据 |
| 有明确受影响候选但存在歧义 | 仅抑制候选事项，登记 pending_conflict | 当前原话、歧义与需要确认的候选 |
| 无法定位 | 保存原话，标记解析未知；不假称已修订或精确抑制 | 原话和未处理状态，不能只输出旧结构化值 |

小模型只能提出 subject/value 候选，提交端仍核对范围、原话、事项版本和依赖；仅“value 是原话子串”不足以证明它脱离条件后仍是用户要求。未知项影响结果时先消歧。0.4 的通用自然纠正仍未实现，本轮不能因加入投影就标为完成。

## 6. 小模型应补召回能力

保持规则基线默认可独立运行。本地规划最多一次，输入限制为当前问题、授权范围内的少量状态/主题线索与候选；输出信息需要、查询词及已有候选 ID。随后只作一次确定性补检索并重新核验来源，新增原文不再经过第二轮模型压缩。

查询规划要能在首次字面命中不足时发挥作用；只把已命中的条目交给重排不能解决 C09。别名需有明确来源，不把“发消息”硬编码成“电子邮件”。无来源的语义推断不能成为硬状态。规划失败、超时或无收益时回到规则与原文，不暗中新增云端调用。

现有 9B 模型一次冷规划约 7.4 秒，超出 5 秒目标，因此继续默认关闭。更小模型、嵌入索引或暖驻策略需另做增益/资源/取消实测；不因架构图中有小模型就自动下载或启用。前台与后台的全部推理成本分别记账。

## 8. 下一轮验证

保留原 11 个场景及原始失败记录作为开发回归；修改后对这些场景的提升单独标为已见集合结果。再冻结新场景：不同编号格式和反选、普通自然纠正后的旧硬状态、无字面重合的同义问法、同源部分修订、紧预算以及删除后的引用。

0.5 已完成 55 个对照请求的真实推理并单独归档；0.4 的五组原始结果仍保留。下一轮须先冻结新增场景，再测通用纠正、语义召回与长历史，不将对这 11 例的修复成绩包装为泛化正确率。

短历史与长历史分开测试。短历史比较完整有效历史，观察新增开销；长历史在相同预算下比较近期窗口、可容纳的完整原文及 LocalMind，报告溢出与缺失，不能截断强基线后仍称“完整历史”。至少覆盖同义、条件、跨会话和多次纠正；固定数据与随机种子，逐例保留答案及真实消息。

同模型、同原话、同范围/删除规则、同预算和输出要求。分别报告任务正确、错误确认、未知、来源完整、输入/输出 tokens、准备失败、冷/暖延迟与全部规划成本。核验“来源还在”“已送入模型”“答案采用正确”三个环节，不再以单元测试数量代替实际收益。
